# ReCarbon — Proposed Architecture (Apple Silicon)

Status: **proposal, not implemented.** Read [FEASIBILITY.md](FEASIBILITY.md) first. This
architecture is for the **Xbox 360** release (title 0x454107EC). ROADMAP M0 verified its
`default.xex`. The appendix covers the original-Xbox release, which is out of scope.

## 1. Approach

We build this as a fork of SpeedBreaker, the static recompilation of NFS: Most Wanted (2005, Xbox 360).
We don't rewrite it from scratch. SpeedBreaker's CPU translation (XenonRecomp plus 8 patches), its PM4/Xenos
renderer, its XMA audio, its SDL3 input and its macOS packaging are game-agnostic in their core.
The game-specific layer is thin and isolated: `runtime/game/`, the midasm hooks in the TOML
config, the ultrawide/edge-bar code in the renderer, and the install manifest. We replace that
layer for Carbon.

```
 default.xex (player's own disc, never in git)
        │  XenonRecomp + SpeedBreaker patches 0001–0008 + ReCarbon 0009 (eqv/dcbst/bdnzt)
        │  config/recarbon.toml + switch_tables*.toml   (regenerated by survey/ scripts)
        ▼
 ppc/*.cpp  ── clang (Homebrew LLVM), -mcpu=apple-m* ──►  ReCarbonRecompLib (static)
                                                              │
 ┌────────────────────────────── runtime (from SpeedBreaker) ─┴──────────────────────────────┐
 │ cpu/      guest context, indirect calls, guest timebase (49.875 MHz)                      │
 │ kernel/   Xbox kernel + XAM exports, threads, sync objects, VFS, memory (Unleashed-derived)│
 │ gpu/      PM4 command processor, Xenos ucode → GLSL → SPIR-V, EDRAM/resolve, textures     │
 │ video/    Vulkan presenter → MoltenVK → Metal; vblank lock; FSR1; gamma                   │
 │ apu/      XMA contexts → FFmpeg (XMA-only libavcodec) → XAudio render driver → SDL3 audio │
 │ hid/      XamInput* → SDL3 gamepad / keyboard map, rumble                                 │
 │ install/  disc verify + install   ← parametrized with a Carbon manifest                   │
 │ ui/       ImGui settings / installer   ← rebranded                                        │
 │ game/     ★ Carbon-specific hooks (new): frame pacing, render queue, movies, widescreen   │
 └───────────────────────────────────────────────────────────────────────────────────────────┘
        ▼
 ReCarbon.app  (arm64, macOS 15+, ad hoc signed, MoltenVK 1.4.2 bundled)
```

## 3. Subsystem plan

### 3.1 CPU (static recompilation)
- Use XenonRecomp at SpeedBreaker's pinned base `ddd128bc`, with all 8 SpeedBreaker patches plus ReCarbon 0009 (`eqv`, `dcbst`, `bdnzt`; done in M1). Patches 0002 (FPCR
  width), 0005 (memory barriers → fences) and 0008 (`mftb` timebase on `cntvct_el0`) are
  essential on arm64.
- Regenerate per-binary inputs with SpeedBreaker's survey pipeline:
  - `xexsurvey` gives the save/restore helpers and the import list.
  - XenonAnalyse, then `fix_switch_tables.py`, then `find_missing_tables.py`, gives the jump tables.
  - `leaf_switch_bounds.py` gives the `functions`.
  - `find_entry_points.py` gives the `secondary_entries`.
  - `setjmp`/`longjmp` are found by hand.
  - ReCarbon additions from M1:
    - `survey/layout.py` reads the address ranges from the surveyed XEX;
    - `b +4` tail-call stubs are bounded automatically;
    - byte-offset jump tables are decoded;
    - SEH headers are declared as `invalid_instructions`.
  - `scripts/survey.sh` runs the whole pipeline reproducibly.
- Keep all optimization flags off (`*_as_local = false`) until boot is proven, as SpeedBreaker does.
- Add each missing PPC/VMX instruction as a new generic XenonRecomp patch. Test it with
  hand-computed cases in `tests/instr/` (`tests/run_instr_tests.sh`).

### 3.2 Kernel / XAM
- Reuse SpeedBreaker's kernel wholesale. `scripts/gen_import_stubs.py` turns every import that
  isn't implemented into a logged `UnimplementedImport` stub. That gives a measurable to-do list
  from the first link.
- Parametrize the title-specific constants: title ID, save paths, content/profile names. Use
  the names in §0 for the environment-variable prefix, user folder and thread names.

### 3.3 GPU
- The PM4 command processor and the Xenos shader translator are hardware-level, so they work for any game.
- Before relying on the renderer, close the known gaps:
  - Texture formats outside the current table: CTX1, DXT3A/5A, `_AS_16`/`_EXPAND`.
  - Memexport-only draws.
  - EDRAM format aliasing.
- Disable the MW-only features at first: the ultrawide/Vert+ front-end detection (fetch constant
  95, `FrontEndScale` hooks), the edge bars, and the pitch-window render-scale heuristic. Start
  Carbon at 1x and 16:9.
- Reintroduce render scaling and widescreen per Carbon target, after surveying its render
  targets.

### 3.4 Audio / movies / input
- Reuse the XMA path as-is: kernel-level XMA contexts, FFmpeg XMA decoder, SDL3 audio. EA's
  stream-player ring semantics, already handled for MW, likely carry over (inferred).
- Movies: the 360 disc ships 65 `.wmv` files, played by the XDK's XMV player (`XMEDIA` is
  linked). This is the same path as MW: decoding runs in recompiled guest code, and the host
  side needs only pacing hooks (`game/movie_pacing.cpp` logic, new addresses).
- Input: reuse `hid/`, with a Carbon default key map. Layering and the path to customization
  are in §3.6.

### 3.5 macOS / Apple Silicon (MacBook Air M5)
- Build with Homebrew LLVM, macOS 15 deployment target, MoltenVK 1.4.2 bundled, ad hoc signing
  (SpeedBreaker `scripts/macos/make_app.py`).
- Two MacBook Air specifics to plan for:
  - **No fan.** Sustained load throttles. Use SpeedBreaker's thermal-aware frame-rate policy
    (Auto 60/30) and default to 1x scale.
  - **Unified memory.** Guest RAM is imported zero-copy through `VK_EXT_external_memory_host`
    where MoltenVK allows it.
- Use `-mcpu=apple-m4` or newer for the recompiled library. Validate with a generic `armv8.5-a`
  build first.

### 3.6 Input (M5 baseline, M8 customization)
M5–M7 keep SpeedBreaker's input as it is, including its keyboard rebinding (Settings > Controls
and the `[keys]` table of `settings.toml`, fully working). M8 extends that rebinding with
profiles, presets and switching on the same layers, without reworking them. Today's `hid/` (from SpeedBreaker) already has most of the parts:
`hid/input.cpp` samples SDL3 and answers `XamInputGetState`, and `hid/key_map.h` turns held keys
into buttons, triggers and stick axes (header-only, SDL-free, tested by `key_map_test`). The
controller side is a fixed SDL-to-XInput table in `input.cpp`.

Three layers, each with one job:

| Layer | Does | Doesn't |
|---|---|---|
| **Device input** | Reads SDL3 keyboard and gamepad state and normalizes it into device events (key codes, gamepad buttons and axes). Hot-plug and focus. | Know about Xbox controls or the game. |
| **Binding resolution** | Applies a mapping to the device state: which keys or pad inputs drive which of the 24 Xbox 360 controls (`keymap::Control`), plus deadzones and how keys combine into axes. | Read devices, or know the game. |
| **Virtual controller** | Assembles one XInput state (`XAMINPUT_STATE`: buttons, triggers, sticks), the packet number and rumble. That's all the guest sees through `XamInputGetState`. | Know where a value came from. |

Today these are logical layers inside `hid/input.cpp`, not separate code (ARCHITECTURE_REVIEW
F12). They're to be kept separable. The two seams M8 needs are a keyboard mapping read as a value
instead of per-frame `settings::GetInt` calls, and the controller table moved into a tested header
(ARCHITECTURE_REVIEW R2, R3). Both are behaviour-preserving.

Rules for M5 so that M8 is an addition, not a refactor:
- **A mapping is data.** The binding layer takes a mapping (a keyboard mapping or a controller
  mapping) as a value: a table from device inputs to `keymap::Control`. Until M8 the keyboard
  mapping comes from the defaults plus `[keys]`, as today, and the controller mapping is the
  default. M8 loads, saves and switches whole mappings.
- **Keyboard and controller mappings are separate types.** M8's separate profiles are then just
  one stored mapping of each.
- **No game logic in input.** No Carbon address, no menu or race state in `hid/`. Game-specific
  things (e.g. a different default for menus) belong in a mapping, never in a code path.
- **The default mappings are the regression baseline.** They're recorded as tables, and unit
  tests pin them. M8's "reset to default" restores those tables, and the tests must pass
  unchanged.
- **Keep existing rebinding working.** Settings > Controls and `[keys]` are not hidden, disabled
  or removed in M5–M7, and their behaviour doesn't change.
- **Not until M8:** no profile manager, presets or profile switching. M8 extends the existing
  rebinding into profiles and migrates an existing `[keys]` table into the keyboard profile, so
  no setting is lost.

M8 adds, on top of the binding layer and the existing rebinding:
- persistent, separate keyboard and controller profiles in the user folder;
- user-defined mappings per profile (the controller gains rebinding);
- WASD and Arrows keyboard presets (mappings);
- manual switching;
- reset to default;
- migration of `[keys]` into the keyboard profile.

## 4. Licensing and repository hygiene
- The project is GPL-3.0-or-later, because the runtime is derived from SpeedBreaker and
  Unleashed Recompiled. Keep `COPYING`, `NOTICE`, `THIRD_PARTY_NOTICES.md` and `LICENSES/`.
  A binary release must offer the LGPL sources (FFmpeg, libmspack).
- No game code, data, decrypted images or generated code in git. The installer verifies the
  player's own disc. The runtime decrypts and decompresses the player's own XEX with
  XenonRecomp's loader at launch, as SpeedBreaker does.

## Appendix — if we target the original Xbox disc instead

The supplied XBE is x86-32 (Pentium III), built with XDK 5849, and links D3D8, DSOUND and XGRAPHC
statically. Its GPU is the NV2A. **No SpeedBreaker component except the platform shell
(SDL3, ImGui, the Vulkan presenter, the installer framework) applies.** Here is what such a port
would need:
- **CPU:** a new x86-32 → arm64 static recompiler. No proven tool exists for XBE comparable to
  XenonRecomp (to verify before committing). Dynamic translation such as xemu's TCG is ruled out
  by the "no runtime CPU emulation" constraint.
- **Kernel:** an original-Xbox kernel HLE covering 126 kernel imports. Cxbx-Reloaded is a
  reference (GPL-2.0; licence compatibility to check).
- **GPU:** either an NV2A pushbuffer → Vulkan translator (as in xemu), or HLE hooks on the
  statically linked D3D8 library (as in Cxbx-Reloaded), mapped onto Vulkan.
- **Audio:** DSOUND / MCPX APU HLE, plus the DOLBY section's encoder.

This is a separate, much larger research project. See FEASIBILITY.md Appendix A.
